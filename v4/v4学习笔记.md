## 2026-03-07 Session 1：认识 Next.js 与 V4 的入口结构

### 1. 今天学什么
- Next.js 是什么。
- 它和 `v3` 的 React + Vite 是什么关系。
- 为什么 `v4` 用 `app/` 目录，而不是 `src/`。

### 2. 核心概念
- **Next.js** 不是用来替代 React 的另一套前端语言，它更像是“React 的上层工程框架”。
- `v3` 里，React 负责页面逻辑，Vite 负责开发服务器和打包。
- `v4` 里，Next.js 把 React、路由、构建、静态生成、metadata 这些常见能力打包进了一套统一规则里。
- 所以现在不是“从 React 跳到别的东西”，而是“在 React 外面加了一层更完整的应用框架”。
- Next.js 不是为了把简单事情故意搞复杂，而是为了把“页面、路由、数据、渲染位置、SEO”这些职责拆开管理。
- 这种拆分的真正价值是控制复杂度：项目小时不明显，项目一大，不拆就会乱、慢、难维护。
- 你可以把它理解成：`v3` 更像“浏览器里的 React 应用”，`v4` 更像“React 被放进了一套应用框架里”。
- 一个还算靠谱的类比是：
  - `HTML / CSS / JS`：像直接在一张 A4 纸上摆内容和交互。
  - `React + TS`：像在 A4 纸外面加了一个工作间，专门管理组件、状态、类型和数据流。
  - `Next.js`：不是把工作间单纯打散，而是把“路由、页面、服务端、客户端、SEO、构建”这些原本容易混在一起的职责重新编排，并规定它们该怎么协作。
- 所以更准确的说法不是“Next.js 让你知道工作间如何具体运作”，而是“Next.js 直接把工作间的一部分规则标准化了，你不用再自己发明整套运行方式”。

### 3. 代码位置
- 首页入口：`v4/app/page.tsx`
- 全局外壳：`v4/app/layout.tsx`
- 详情页入口：`v4/app/elevators/[id]/page.tsx`
- 当前首页文案改动位置：`v4/app/page.tsx`

### 4. 我自己复述
- Next.js = React + 一整套官方规定好的项目组织方式。
- `app/` 不是普通文件夹，它会直接影响路由。
- `page.tsx` 代表某个页面入口，`layout.tsx` 代表包住页面的公共外壳。
- Next.js 这样拆分，不是为了拆而拆，而是为了把服务端该做的事、浏览器该做的事、页面结构、路由结构分别管清楚。

### 5. 小改动结果 / 当前疑问
- 已完成一个最小可见改动：在首页说明区新增了一句学习提示文案，用来确认 `app/page.tsx` 的确就是首页入口。
- 已补充一条理解：Next.js 的拆分本质是“管理复杂度”，不是“增加复杂度”。
- 已记录一个真实排错案例：浏览器扩展给 `<html>` 注入属性，会导致 Next.js 出现 hydration mismatch，看起来像代码炸了，其实是服务端 HTML 和客户端接管时对不上。
- 当前疑问：
  - 为什么 `app` 目录能直接变成路由？
  - 为什么这里没有 `main.tsx`？
  - 为什么同一个项目里，有些代码更适合放服务端，有些代码必须放浏览器？

## 2026-03-07 Session 2：文件路由与页面文件职责

### 1. 今天学什么
- 什么是文件路由。
- `layout.tsx`、`page.tsx`、`app/elevators/[id]/page.tsx` 分别负责什么。
- 为什么 `v4` 没有 `main.tsx`，但页面还是能直接显示。

### 2. 核心概念
- 在 Next.js 里，`app/` 目录不是普通文件夹，而是“路由地图”。
- `app/page.tsx` 自动对应首页 `/`。
- `app/elevators/[id]/page.tsx` 自动对应动态详情页 `/elevators/1`、`/elevators/2` 这类地址。
- `layout.tsx` 不负责某一个页面内容，而是负责包住所有页面的共同外壳。
- 所以 `v4` 不再需要 `main.tsx` 自己手动挂载 React 根节点，Next.js 已经把页面入口规则内置好了。

### 3. 代码位置
- 全局布局：`v4/app/layout.tsx`
- 首页路由：`v4/app/page.tsx`
- 详情页动态路由：`v4/app/elevators/[id]/page.tsx`
- 404 兜底页：`v4/app/not-found.tsx`

### 4. 我自己复述
- `layout.tsx` 像整栋楼的公共走廊和外壳。
- `page.tsx` 像某个具体房间的内容。
- `[id]` 不是普通目录名，而是告诉 Next：“这里是一个变量路由参数”。
- 所以文件结构在 Next.js 里不只是整理代码，它本身就是功能定义。

### 5. 小改动结果 / 当前疑问
- 已完成一个最小可见改动：在详情页新增提示文案，用来确认详情页入口文件是 `app/elevators/[id]/page.tsx`。
- 当前疑问：
  - `layout.tsx` 是不是每一级目录都能有？
  - `not-found.tsx` 为什么不需要手动 import？
  - 动态路由参数为什么通过 `params` 传进来？

### 6. 这一节的结构理解补充
- 当前真正要记住的不是所有细节，而是 4 个页面文件的分工：
  - `layout.tsx`：全站外壳
  - `app/page.tsx`：首页列表页
  - `app/elevators/[id]/page.tsx`：详情页控制中心
  - `not-found.tsx`：找不到页面时的兜底页
- 它们之间的运作关系可以简化成两条链：
  - 访问 `/` -> `app/page.tsx` -> 被 `layout.tsx` 包住 -> 显示首页
  - 访问 `/elevators/3` -> `app/elevators/[id]/page.tsx` -> 取 `id` -> 查数据 -> 找不到就 `notFound()` -> 显示 `not-found.tsx`
- 当前项目里，文件结构不只是“摆放代码”，它本身就是功能定义的一部分。

## 2026-03-07 Session 3：开始补语法眼镜（以 layout.tsx 为例）

### 1. 今天学什么

### 3. 代码位置

### 4. 我自己复述

### 5. 当前疑问
- `export default` 和普通 `export` 有什么区别？
- `children` 为什么会自动传进来？
- `: Metadata` 这种冒号后面的东西到底是不是“声明变量类型”？

### 6. 关于“框架按文件约定自动调用”是怎么运作的
- 这里不是“我手动 import 了 `RootLayout` 并调用它”，而是 **Next.js 框架自己在背后按规则接线**。
- 整个过程可以先粗暴理解成 4 步：
  1. **扫描 `app/` 目录**
     - Next.js 启动或构建时，会查找 `layout.tsx`、`page.tsx`、`not-found.tsx` 这类约定文件。
  2. **整理成一棵路由树**
     - 它不会只记“有这些文件”，而是会把它们组装成内部页面树。
  3. **按路由树自动组装布局和页面**
     - 访问 `/` 时，Next.js 会做出类似：
       `RootLayout -> HomePage`
     - 访问 `/elevators/3` 时，会做出类似：
       `RootLayout -> DetailPage(params={ id: "3" })`
  4. **最后再交给 React 渲染**
     - Next.js 决定“怎么组装页面”
     - React 负责“把组装好的页面画出来”

- 所以你全局搜索不到 `RootLayout` 的显式调用位置，是正常的。
- `RootLayout` 的调用方不是你的业务代码，而是 Next.js 框架本身。
- `children` 也不是你手动传进去的，而是 Next.js 在渲染布局时，把当前匹配到的页面内容自动塞给 `RootLayout`。

### 7. 在哪里能看到“具体运作”
- 当前最适合看的，不是框架源码，而是生成产物：
  - `v4/.next/server/app/page.js`
- 这个文件里能看到 Next.js 已经把：
  - `app/layout.tsx`
  - `app/page.tsx`
  - `app/not-found.tsx`
  这些文件整理成内部树结构。
- 所以“自动调用”的本质不是魔法，而是：
  - **约定**
  - **扫描**
  - **组装**
  - **渲染**

### 8. 当前阶段总结
- **已经完成的阶段**
  - Session 1：认识 Next.js 是 React 的上层应用框架，理解 `app/` 目录不是普通目录。

  - Session 3（当前进行中）：开始补“语法眼镜”，重点解决“知道文件职责，但看不懂每行代码语法”这个问题。

- **当前真实所处位置**
  - 你已经跨过了“完全不知道 Next.js 是什么”的阶段。
  - 你现在处在 **“结构理解已建立，但语法细节还不稳”** 的阶段。
  - 也就是说，当前不是继续猛学新框架概念的时候，而是要补足：

## 2026-03-07 Session 5：首页数据流与组件传参

### 1. 今天学什么
- 首页 `page.tsx`、`ElevatorCatalog`、`ElevatorCard` 三者的分工。
- 为什么首页是“服务端拿数据 + 客户端做交互 + 子组件做展示”。
- 组件标签传参语法：`<ElevatorCard elevator={elevator} />`

### 2. 核心概念
- 首页主线可以简化成：
  - `app/page.tsx`：先拿全量数据
  - `ElevatorCatalog`：在客户端维护筛选状态并控制列表
  - `ElevatorCard`：负责单张卡片展示
- 这就是职责拆分的一个实际例子：不是一个页面包打天下，而是按“拿数据 / 管状态 / 画单项”分开。

### 3. 代码位置
- 首页入口：`v4/app/page.tsx`
- 客户端目录组件：`v4/components/elevator-catalog.tsx`
- 单张卡片组件：`v4/components/elevator-card.tsx`

### 4. 我自己复述
- `page.tsx` 先通过 `getElevators()` 拿到全量数据，再把数据交给 `ElevatorCatalog`。
- `ElevatorCatalog` 不是自己拿数据，而是接收数据，然后在浏览器里做筛选和列表控制。
- `ElevatorCard` 只接收一条电梯数据，然后把它渲染成一张卡片。
- `<ElevatorCard elevator={elevator} />` 的意思是：使用 `ElevatorCard` 组件，并传入一个名叫 `elevator` 的参数，参数值就是当前变量 `elevator`。

### 5. 小语法补充
- 组件标签大写开头时，通常表示这是自定义组件，不是原生 HTML 标签。
- `属性名={变量}` 这种写法是在给组件传 `props`。
- `<ElevatorCard elevator={elevator} />` 中：
  - 左边的 `elevator=` 是传参名
  - 右边的 `{elevator}` 是当前变量值
  - `/>` 表示这是一个没有内部子内容的自闭合组件标签

## 2026-03-07 Session 7：筛选结果是怎么自动更新的

### 1. 今天学什么
- `filteredElevators` 是怎么来的
- `useMemo` 在这里做什么
- 为什么筛选状态一变，列表就跟着变

### 2. 核心概念
- 当前显示的列表不是一份写死的数据，而是由：
  - 原始电梯数组 `elevators`
  - 当前筛选条件 `filters`
  计算出来的结果。
- `filterElevators(...)` 负责真正做筛选计算。
- `useMemo` 负责把这个计算结果“记一下”，只有依赖变了才重新算。

### 3. 代码位置
- 客户端筛选组件：`v4/components/elevator-catalog.tsx`
- 共享筛选逻辑：`v4/lib/elevator-shared.ts`

### 4. 我自己复述
- 用户改筛选 -> `filters` 状态变化
- 状态变化 -> 组件重新渲染
- `useMemo` 发现依赖变了 -> 重新执行 `filterElevators(...)`
- 新的 `filteredElevators` 出来 -> 列表重新渲染

## 2026-03-07 Session 8：高频语法补完 2

### 1. 今天学什么
- 箭头函数 `=>`
- `.map()`

### 2. 核心概念
- 箭头函数本质上还是函数，只是写法更短。
- `.map()` 的作用不是筛掉元素，而是“把数组中的每一项变成一个新结果”。
- 在 React / Next.js 里，`.map()` 最常见的用途就是：
  - 把数据项
  - 变成组件列表

### 3. 代码位置
- `v4/components/elevator-catalog.tsx`

### 4. 我自己复述
- `(key, value) => { ... }` 这种写法，本质上就是定义一个函数。
- `filteredElevators.map((elevator) => (...))` 的意思是：
  - 把筛选后的每一条电梯数据
  - 逐条转换成一个 `ElevatorCard` 组件

### 5. 当前疑问
- 暂时无

首先是简单的html/css/js
就像是在一张A4纸上将各个模块放在上面进行互动
接着react和ts则是对这些模块进行提前处理，就是在A4纸外面加一个工作间，用来调度数据，以便灵活地展示A4纸上的内容
最后是nextjs，它则是直接把这个工作间给打散，但相互之间的联系还在，只是让你知道这整个工作间是如何具体运作的

**文件关系：**
**第一层：先看页面骨架**

- [layout.tsx](app://-/index.html?hostId=local)
- [page.tsx](app://-/index.html?hostId=local)
- [page.tsx](app://-/index.html?hostId=local)
- [not-found.tsx](app://-/index.html?hostId=local)

这几个文件是 Next.js 最核心的“页面层”。

它们的关系是：

- layout.tsx：全站外壳，包住所有页面
- app/page.tsx：首页 /
- app/elevators/[id]/page.tsx：详情页 /elevators/1、/elevators/2 这类动态路由
- not-found.tsx：找不到页面时的兜底页

可以把它理解成：

- layout.tsx 是楼体
- page.tsx 是具体房间
- [id]/page.tsx 是一类可变房间
- not-found.tsx 是“无此房间”的提示牌

**第二层：再看数据和组件怎么接起来**

- [elevator-data.ts](app://-/index.html?hostId=local)
- [elevator-shared.ts](app://-/index.html?hostId=local)
- [types.ts](app://-/index.html?hostId=local)
- [elevator-catalog.tsx](app://-/index.html?hostId=local)
- [elevator-card.tsx](app://-/index.html?hostId=local)

它们的关系是：

- types.ts：先定义“电梯数据长什么样”
- elevator-data.ts：读数据，偏服务端
- elevator-shared.ts：放共享逻辑，比如筛选和格式化
- elevator-catalog.tsx：客户端筛选区和列表区
- elevator-card.tsx：单张卡片怎么渲染

首页的数据流可以简化成：  
app/page.tsx -> getElevators() -> ElevatorCatalog -> ElevatorCard

详情页的数据流可以简化成：  
app/elevators/[id]/page.tsx -> 读取路由参数 id -> getElevatorById() -> 渲染详情页

**第三层：最后看工程入口，不用深挖**

- [package.json](app://-/index.html?hostId=local)
- [tsconfig.json](app://-/index.html?hostId=local)
- [next-env.d.ts](app://-/index.html?hostId=local)
- [globals.css](app://-/index.html?hostId=local)

这些文件的关系是：

- package.json：怎么启动、构建项目
- tsconfig.json：TypeScript 规则
- next-env.d.ts：Next 自动用的类型声明
- globals.css：全局样式

你现在不需要深究它们内部细节，只要知道它们在“托底”。

**哪些文件现在可以先不看**

- .next/
- node_modules/
- package-lock.json

这些不是学习 Next.js 核心思路的地方。
