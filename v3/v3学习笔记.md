## 2026-03-06 Session 1：认识工程化结构与组件树

### 1. 核心文件认知（C 语言类比版）
- **`package.json`**：相当于 **`Makefile`** 或 **`CMakeLists.txt`**。记录了项目的依赖清单（采购单）和运行指令（脚本）。
- **`src/` 文件夹**：**生产车间**。把原本的长文本 HTML 拆成了“积木段落”（组件），方便复用和独立渲染。
- **`node_modules/`**：**私人工具箱**。每个项目独立存放自己的依赖库，避免全局版本冲突。
- **`dist/`**：**出厂成品 (.exe)**。浏览器看不懂 TS，构建工具（Vite）会将 `src` 编译压缩成 `dist` 里的标准 JS/HTML。

### 2. 组件树（层级关系）
- **App (根节点)**：掌管全局数据和状态（如筛选条件、选中项）。
- **FilterBar (子组件)**：负责接收用户输入，并把变化告诉 App。
- **ElevatorGrid -> ElevatorCard**：数据驱动的列表，App 给多少数据，就生成多少个卡片。
- **ElevatorModal**：独立的弹窗组件。

### 4. 工程化思维（进阶认知）
- **不要手写配置文件**：`package.json`、`tsconfig.json` 等是由 **“脚手架 (Scaffolding)”**（如 Vite）自动生成的。开发者只需在生成的模板上做“手术”。
- **黑盒思维 (Black Box)**：不需要（也不应该）一次性看懂所有代码。只需关注：
    1. **`types.ts`**：数据的规则书。
    2. **`App.tsx`**：组件的组装台。

## 2026-03-06 Session 2：Props 与 开发环境排坑

### 1. 致命陷阱：`dist` (成品) vs `src` (车间)
- **现象**：修改了 `src/components/ElevatorCard.tsx` 里的代码，网页纹丝不动。
- **根源**：浏览器访问的是 `v3/dist/index.html`。那是之前 `npm run build` 生成的“静态尸体”，它不会感应到你对源码的修改。
- **解决**：必须运行 `npm run dev`，访问 Vite 提供的 `http://localhost:5173`。这才是“实时车间”，支持 **HMR (热更新)**，保存即生效。

### 2. Props（数据传递）的三级跳
数据从 JSON 变成界面上的文字，经历了三步显式传递：
1. **App.tsx**：`<ElevatorGrid elevators={filteredElevators} />` —— **发货**。把过滤后的数组传给 Grid。
2. **ElevatorGrid.tsx**：`<ElevatorCard elevator={elevator} />` —— **分发**。用 `.map` 循环，给每个卡片塞进一个电梯对象。
3. **ElevatorCard.tsx**：`function ElevatorCard({ elevator })` —— **收货**。通过“解构赋值”拿到电梯数据并展示。

## 2026-03-06 Session 3：State (组件记忆) 与 随机看看

### 1. 数据流向拆解（从“点击”到“弹窗”）
1. **触发源 (Trigger)**：用户点击 `<button onClick={handleRandom}>`。
2. **逻辑层 (Logic)**：`handleRandom` 计算出一个随机索引，并从 `filteredElevators` 数组中取出一个电梯对象。
3. **写入记忆 (State Update)**：调用 `setSelectedElevator(随机电梯对象)`。
   - 这行代码就像是在 React 的“活页夹”里把 `selectedElevator` 的值从 `null` 改成了具体的“电梯数据”。
4. **自动渲染 (Re-render)**：React 检测到 `selectedElevator` 变了，立刻命令 `App` 组件重新刷漆。
5. **分发展示 (Props Delivery)**：`App` 把新的 `selectedElevator` 传给 `<ElevatorModal elevator={selectedElevator} />`。
6. **结果 (UI)**：`ElevatorModal` 收到包裹后，由于数据不再是 `null`，它就会自动在屏幕上弹出来。

### 2. 对比：错误的方式 vs 正确的方式
- **❌ 错误方式 (传统 DOM 思路)**：
  ```javascript
  // 这种写法在 React 里是“禁忌”，因为它绕过了 React 的管理
  const btn = document.querySelector('.random-btn');
  btn.onclick = () => {
    const modal = document.querySelector('#modal');
    modal.style.display = 'block'; // 手动操作 DOM
    modal.innerText = '随机电梯A';
  };
  ```
- **✅ 正确方式 (React 状态驱动)**：
  ```tsx
  // 只管改数据，不管改界面
  const [selected, setSelected] = useState(null);
  const handleRandom = () => setSelected(data[0]); // 改了数据，界面自动随之起舞
  ```

## 2026-03-06 Session 5：Effect (副作用) 与 筛选记忆

### 1. 目标：持久化筛选状态
- **核心逻辑**：将 `filters` 状态实时同步到浏览器的 `localStorage` 中，并在页面加载时自动读取。
- **作用**：即使刷新页面或关闭浏览器，用户的筛选偏好（国家、品牌、关键字等）依然能被找回。

### 2. 代码流向拆解 (useEffect 的全生命周期)
1. **监听 (Dependency)**：在 `App.tsx` 中使用 `useEffect(..., [filters])`。React 会持续盯着 `filters` 变量。
2. **触发 (Trigger)**：用户改变了筛选（如输入搜索词）。
3. **执行 (Action)**：`useEffect` 内部的代码被激活，将 `filters` 转化为 JSON 字符串并存入 `localStorage`。
4. **回溯 (Initial Load)**：
   - 页面刷新。
   - `getSavedFilters()` 函数在 `useState` 初始化时运行。
   - 从 `localStorage` 拿出字符串 -> 解析回对象 -> 成为 React 的初始状态。

### 3. 副作用 (Side Effect) 的本质
- **定义**：React 的主职是“渲染 UI”。任何超出“根据数据画图”范围的操作（如改存储、发请求）都叫副作用。
- **管理**：如果不放在 `useEffect` 里，这些操作可能会在每次重绘时反复执行，导致性能崩溃或死循环。
###  4. 核心感悟
**数据是活的，存储是死的**。`useEffect` 就像是一根导线，把“活”的    │
│     React 状态导流进“死”的硬盘存储中。

## 2026-03-06 Session 6：TS 进阶 —— 字面量联合类型

### 1. 目标：从“能跑”到“严谨”
- **核心逻辑**：不再使用宽泛的 `string`，而是定义精确的 `ElevatorCountry` 和 `ElevatorType` 联合类型。
- **作用**：在编写代码时，由编译器（TS）而非运行时的用户来发现拼写错误。

### 2. 核心变化对比
- **重构前**：`country: string`。你可以写任何字符串，比如 `"中过"`。代码能运行，但筛选功能会失效。
- **重构后**：`country: ElevatorCountry`。如果你写 `"中过"`，编辑器立刻划红线报警，代码无法通过编译。

### 3. 工程化思维：类型即文档
- **智能提示**：定义了联合类型后，打出 `elevator.type = ""` 时，IDE 会自动弹出所有合法选项。
- **强制约束**：这是一种“防御性编程”，确保数据的消费端（代码）永远符合数据的生产端（JSON）的规范。

## 2026-03-06 Session 7：UI/UX 增强 —— 键盘与点击策略

### 1. 目标：工业级交互细节
- **核心逻辑**：通过监听 `window` 的键盘事件（ESC）和利用事件冒泡机制（stopPropagation），实现更自然、更符合用户直觉的弹窗交互。
- **作用**：让 Web 应用摆脱“简陋网页感”，提升到“原生应用”级别的体验。

### 2. 技术要点拆解
- **useRef (DOM 钩子)**：用于在弹窗打开时自动聚焦到“关闭”按钮。React 负责渲染，Ref 负责“下达命令”（手动控制焦点）。
- **事件冒泡与拦截**：
  - 点击背景（Backdrop）触发关闭。
  - 点击内容区（Panel）必须拦截冒泡，否则点击弹窗内部也会导致弹窗关闭（误杀）。
- **useEffect 清理函数**：键盘监听是挂载在 `document` 上的全局副作用，必须在组件销毁时手动解绑，否则会造成内存泄漏。

### 3. 工程化思维：交互即细节
- **焦点管理 (Focus Management)**：好的弹窗不应该让用户的焦点在按下 Tab 键后“飞出”弹窗范围。
- **内存安全**：所有全局监听都必须有“对应的卸载动作”，这是编写稳健代码的基本修养。

## 2026-03-06 Session 8：阶段性大复盘 —— 从零件到系统

### 1. 通关回顾：我们走过的路
- **Session 1-2**：理清了项目的物理结构，学会了在“实时车间”（Dev Server）里干活，掌握了 Props 数据接力。

### 2. 核心架构认知：数据一致性
- **唯一真理来源**：数据永远存在 App.tsx 的 State 里，其他地方看到的都是它的影子（Props）或它的变体（Derived State）。
- **声明式编程**：我只管描述“数据现在是什么样”，React 负责把“界面变成什么样”。

### 3. 开发者修养
- **不删除，只追加**：在学习过程中保持记录的完整性，就是保留自己的成长痕迹。
- **类型优先**：先定义好 Data 和 Types，逻辑自然顺理成章。
